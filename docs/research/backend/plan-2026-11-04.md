## 2. Principles (sustainable and scalable)
1. Three kinds of data, three treatments: **reference corpus** (immutable, public text; Postgres read-only, cached at the edge), **editorial content** (written and reviewed in git, served from the database through a publish step), **user data** (per user, row-level security, local-first with sync).
2. **Git stays where content is authored and reviewed** (dossier → converter → validated JSON); the database is where the site **reads** it. Publishing is a script, idempotent, hash-checked (the manifest pattern of `load-corpus.mjs`).
3. **Every source behind an interface with two implementations** (`local` for tests and offline work, `supabase` for production), selected by an environment variable, as the Bible already does. The e2e suite keeps running on `local`; one extra run on `supabase` checks parity.
4. **Cache, do not query per request:** pages are static or ISR/`use cache` with tags; the database is the origin, not a per-request dependency. Vercel functions in `gru1` (São Paulo) next to `sa-east-1`.
5. **Licences drive access:** STEPBible's word data is «do not redistribute»: store it but expose it **only to the server** (no `anon` select policy; rendered pages leak only what a page shows). Corpus tables for public-domain text may have a public read policy; every new table carries its own `grant select` (the Data API exposure change of 2026-10-30).
6. Verify against the current Supabase docs and changelog before each step (skills `supabase` and `supabase-postgres-best-practices`), advisors after every DDL change.

## 4. Decisions for Pedro
1. **Plan.** The free plan has 500 MB and pauses after 7 days of inactivity. Estimated size (from the files, not measured): Bibles + Fathers ≈ 100–150 MB with indexes, words ≈ 120–200 MB (≈ 440,000 tokens, 17,000 lexicon entries with long definitions): near or over the limit. Pro (about 25 USD/month; to be confirmed on the pricing page) never pauses, has daily backups and 8 GB. Recommended once anyone outside the close circle uses it; the free plan is enough for Stage 0–1 meanwhile.
2. **Editorial model:** git authors, database serves (recommended) versus content only in the database (loses the review and validation tooling).
3. **Words access:** server-only (recommended) versus public read.
4. **Auth providers** (e-mail link, Google, Apple?) and whether the notes are available without an account (local-first keeps them working).

## 5. Risks
- The single local copy of the data (above): the first thing to fix.
- The free plan's pause during a demo: restore takes minutes; Pro removes it.
- PostgREST row caps and paging for big chapters/works: the reader already pages by `Content-Range`; test with the largest work.
- Cost of the words aggregates: precompute per-word per-book counts at load time instead of at request time.
- Data API exposure rules (explicit `grant select`), RLS mistakes (security advisor after each migration), secrets (service key only in scripts and server code, never in a client bundle or the repo).
- Content rewrites: the 20 tradition pages and 4 doctrine pages are regenerated by the converters; the publish step must read the generated JSON, not the TypeScript, so a second source of truth does not appear.
