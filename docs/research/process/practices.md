## 1. Anthropic's own guidance

### 1.1 The underlying constraint
- "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." https://code.claude.com/docs/en/best-practices [verified]
- Context engineering = "the set of strategies for curating and maintaining the optimal set of tokens"; goal: the "smallest possible set of high-signal tokens"; recall degrades as the window grows ("attention budget"). Prompts should sit at the "right altitude", between "hardcoding complex, brittle logic" and "vague, high-level guidance that fails to give the LLM concrete signals." https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents [verified]
- Hybrid loading is Anthropic's described pattern: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time." (same URL) [verified]

### 1.2 CLAUDE.md / memory / rules
- Content: "CLAUDE.md is loaded every session, so only include things that apply broadly. For domain knowledge or workflows that are only relevant sometimes, use skills instead." Test per line: "Would removing this cause Claude to make mistakes?" … "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." Failure pattern "The over-specified CLAUDE.md … Fix: Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook." https://code.claude.com/docs/en/best-practices [verified]
- Size and procedure: "target under 200 lines per CLAUDE.md file … Imports … don't reduce its context cost, because imported files also load at launch." "If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule." Memory is "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook." `/doctor prompt-audit` finds "references to files or commands that don't exist, and files that contradict each other." https://code.claude.com/docs/en/memory [verified]
- Path-scoped rules: "A path-scoped rule loads when Claude uses the Read, Write, or Edit tool on a matching file"; "`paths` is the only field Claude Code reads from a rule." Rules without `paths` load at launch. (same URL) [verified]
- Auto memory: "The first 200 lines of `MEMORY.md`, or the first 25KB … are loaded at the start of every conversation"; topic files are read on demand; shared across worktrees of the same repo. (same URL) [verified]
- **Doctrina.** Already follows most of this (AGENTS.md <200 lines, `.claude/rules/ui.md` and `content.md` path-scoped, git guard as PreToolUse hook). Key fact for design: **path-scoped rules fire on file access, not on task type.** A research run touches `docs/research/**` or `data/**`; a rule scoped there would load for *any* session reading those files, including unrelated ones, and would not load for a coordinator that only spawns agents. Note also that Pedro's auto memory (`MEMORY.md`) already holds process lessons ("Subagent model economy", "usage guard", "lessons on agents") — i.e. method knowledge is currently scattered into a per-user store that subagents do not inherit (see 1.4).

### 1.3 Skills (`.claude/skills/<name>/SKILL.md`)
- When to create one: "when you keep pasting the same instructions, checklist, or multi-step procedure into chat, or when a section of CLAUDE.md has grown into a procedure rather than a fact. Unlike CLAUDE.md content, a skill's body loads only when it's used." "If a CLAUDE.md section reads like a recipe, move it into a skill." https://code.claude.com/docs/en/skills [verified]
- Loading: by default "Description always in context. Full skill loads when invoked"; with `disable-model-invocation: true` the description is *not* in context and only `/name` loads it; `paths` limits automatic loading to matching files; `context: fork` runs it in a subagent. Description + `when_to_use` truncated at 1,536 chars. After compaction, "Claude Code re-attaches the most recent invocation of each skill, keeping the first 5,000 tokens," within a 25,000-token shared budget; Claude "doesn't re-read the file." (same URL) [verified via fetch summary]
- Authoring: "Create evaluations BEFORE writing extensive documentation"; evaluation-driven loop (identify gaps → three scenarios → baseline → minimal instructions → iterate). "Claude A" writes/refines, "Claude B" uses it on real tasks; observe "Ignored content: If Claude never accesses a bundled file, it might be unnecessary." Checklists Claude "can copy into its response and check off" (incl. a research-synthesis example ending in "Verify citations"). "Avoid time-sensitive information"; "Keep references one level deep from SKILL.md"; body "under 500 lines." https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices [verified]
- Origin of skill content: ask Claude to "capture its successful approaches and common mistakes into reusable context and code"; a skill is like "an onboarding guide for a new hire." https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills [verified]
- **Doctrina.** Skills are the native mechanism for "load this method only when doing this task type," triggered by description match (auto) or `/name` (manual). Risks: (a) auto-trigger depends on description quality and may miss or misfire; (b) every model-invocable skill's description is paid every turn (Pedro already has ~60 user/plugin skills listed); (c) once loaded, the body persists, so a long playbook in a long run competes for context. Mitigations named by Anthropic: `disable-model-invocation`, short body + reference files one level deep.

### 1.4 Subagents and custom agents (`.claude/agents/`)
- "Use one when a side task would flood your main conversation with search results, logs, or file contents you won't reference again." Frontmatter: `name`, `description` (required), `tools`, `model`, `skills` ("full skill content is injected"), `memory`, `hooks`, `omitClaudeMd`, etc. https://code.claude.com/docs/en/sub-agents [verified]
- Inheritance: non-fork subagents load the CLAUDE.md hierarchy and AGENTS.md; built-in Explore/Plan "start without your CLAUDE.md files"; "the main conversation's auto memory isn't loaded"; skills are not inherited unless listed in `skills:` (they can still be invoked via the Skill tool). (same URL) [verified]
- Persistent agent memory: `memory: project` → `.claude/agent-memory/<agent>/`, with "the first 200 lines or 25KB of `MEMORY.md` … with instructions to curate `MEMORY.md` if it exceeds that limit"; "`project` is the recommended default scope." (same URL) [verified]
- **Doctrina.** A custom agent per recurring role (e.g. source-verifier, consistency-checker) can preload the method skill via `skills:` and carry its own curated lessons file in `.claude/agent-memory/` (versioned, visible to Pedro). This solves "lessons live in Pedro's MEMORY.md which subagents never see." Cost: one more place where knowledge lives (single-source risk, §3.5).

### 1.5 Hooks
- "Use hooks for actions that must happen every time with zero exceptions … Unlike CLAUDE.md instructions which are advisory, hooks are deterministic." https://code.claude.com/docs/en/best-practices [verified]
- Context-injecting events: SessionStart / SubagentStart ("at the start of the conversation"), UserPromptSubmit ("alongside the submitted prompt"), Stop / SubagentStop ("at the end of the turn. The conversation continues so Claude can act on the feedback"); Stop exit code 2 "Prevents Claude from stopping." Also `InstructionsLoaded`, `PreCompact`, `SessionEnd`, `TaskCompleted`. https://code.claude.com/docs/en/hooks [verified]
- "Put guardrails in hooks. An instruction like 'never edit .env' … is a request, not a guarantee." https://code.claude.com/docs/en/features-overview [verified]
- **Doctrina.** Hooks are the only mechanism that can *force* the loop to close: e.g. a SubagentStart hook that injects "read `docs/playbooks/<type>.md`" by agent type, or a Stop/SessionEnd hook that refuses to end a run whose plan file has an empty "Retro" section. Cost: scripts to maintain; a blocking Stop hook in a 5-hour-capped account can burn usage if it loops (the docs mention a cap on consecutive blocks [verified, best-practices page]).

### 1.6 Plan mode, verification, parallel sessions
- "Separate research and planning from implementation"; Explore → Plan → Implement; but "Plan mode is useful, but also adds overhead … If you could describe the diff in one sentence, skip the plan." Specs should be self-contained: "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step." https://code.claude.com/docs/en/best-practices [verified]
- Verification: "Claude stops when the work looks done"; second-opinion verification "has a fresh model try to refute the result, so the agent doing the work isn't the one grading it"; but a reviewer "prompted to find gaps will usually report some, even when the work is sound … Chasing every finding leads to over-engineering." (same URL) [verified]
- Fan-out: "Test on a few files, then run on all of them … Refine your prompt based on what goes wrong with the first 2-3." (same URL) [verified]
- Triggers for adding each mechanism ("Build your setup over time"): "Claude gets a convention or command wrong twice → Add it to CLAUDE.md"; "You paste the same playbook or multi-step procedure into chat for the third time → Capture it as a skill"; "You want something to happen every time without asking → Write a hook." "A repeated mistake or a recurring review comment is a CLAUDE.md edit, not a one-off correction in chat. A workflow you keep tweaking by hand is a skill that needs another revision." https://code.claude.com/docs/en/features-overview [verified]
- **Doctrina.** These triggers are exactly a promotion ladder (§4). The pilot-first fan-out rule ("2-3 then all") is directly applicable to research runs on a usage cap.

### 1.7 Long-running agents and multi-agent research (engineering posts)
- Harnesses: each session "begins with no memory of what came before"; failure modes: agents "tried to do too much at once", later agents "declare the job done" too early. Fix: an initializer that writes `claude-progress.txt`, a feature list and an initial commit; each session reads progress + git log, picks one item, verifies, updates notes. Feature list in JSON because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files." Published as a failure-mode → fix table. https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents [verified]
- Multi-agent research: multi-agent systems "use about 15× more tokens than chats"; "token usage by itself explains 80% of the variance" in BrowseComp performance; coding-like tasks with shared context "are not a good fit." Delegation must give "an objective, an output format" plus tools and boundaries, or agents duplicate work. Effort-scaling rules embedded in prompts ("Simple fact-finding requires just 1 agent with 3-10 tool calls"); early failure "spawning 50 subagents for simple queries." Self-improvement: a tool-testing agent rewrote tool descriptions → "40% decrease in task completion time." Lead agent saves its plan to memory because context beyond 200k "will be truncated"; subagents write to files and pass references. Eval: start with "about 20 queries"; humans caught agents preferring "SEO-optimized content farms." "Agents are stateful and errors compound"; resume, don't restart. https://www.anthropic.com/engineering/multi-agent-research-system [verified]
- **Doctrina.** This is the closest analogue to Doctrina's research runs. Directly reusable: explicit effort-scaling table per task type (how many agents, which model, how many tool calls), delegation brief template (objective / output format / tools / boundaries / source-quality rules), plan persisted to a file before fan-out, outputs to files, resume-from-checkpoint (already the "Progress block" convention). The 15× token figure is the quantitative argument for writing a plan before every fan-out on a 5-hour cap.

## 2. Community conventions for agent-driven repos

### 2.1 AGENTS.md (open standard)
- **Prescribes.** "A simple, open format for guiding coding agents"; a README for agents. Suggested contents: overview, build/test commands, code style, testing, security, plus "Commit messages or pull request guidelines, security gotchas, large datasets, deployment steps." No schema: "AGENTS.md is just standard Markdown." Nested files: "Agents automatically read the nearest file in the directory tree, so the closest one takes precedence"; "explicit user chat prompts override everything." Stewarded "by the Agentic AI Foundation under the Linux Foundation." https://agents.md/ [verified]
- **Evidence against overloading it.** Gloaguen et al. (ETH Zurich / LogicStar), "Evaluating AGENTS.md" (arXiv 2602.11988): "providing context files does not generally improve task success rates" while "increasing inference cost by over 20% on average"; agents follow the instructions, but "repository overviews, although popular and recommended by model providers, are not helpful"; useful for "non-standard coding practices"; "any attempts to improve performance should be rigorously evaluated before deployment." https://arxiv.org/abs/2602.11988 [verified, abstract only]. Secondary coverage: LLM-generated files hurt in 5/8 settings; human-written ones ~+4 pp but up to +19% cost, because agents run more tests/greps the file asks for. https://the-decoder.com/context-files-for-coding-agents-often-dont-help-and-may-even-hurt-performance/ [snippet]
- **Doctrina.** Already conforms (AGENTS.md imported by CLAUDE.md, <200 lines, docs on demand). The ETH result argues *against* adding process how-tos to AGENTS.md: every line is paid on every turn of every subagent, and agents obey it even when irrelevant. Process methods should load only for the task type that needs them.

### 2.2 Spec-driven development (GitHub spec-kit, Kiro)
- **spec-kit prescribes.** "Specifications don't serve code—code serves specifications." Phases `/speckit.specify` → `/speckit.plan` → `/speckit.tasks` → implement, each a Markdown file per feature folder; a project **constitution** (`memory/constitution.md`) of non-negotiable articles that every plan is checked against; "Production metrics and incidents don't just trigger hotfixes—they update specifications"; constitutional amendments need "documented rationale, maintainer review, and a backwards-compatibility assessment." https://github.com/github/spec-kit/blob/main/spec-driven.md [verified]
- **Kiro prescribes.** Per-spec `requirements.md` (user stories + EARS acceptance criteria), `design.md`, `tasks.md` under `.kiro/specs/` [snippet: https://kiro.dev/docs/specs/index]. **Steering** files in `.kiro/steering/` with four inclusion modes via YAML frontmatter: `always` (default; `product.md`, `tech.md`, `structure.md` "included in every interaction by default"), `fileMatch` ("included only when working with files that match the specified pattern"), `manual` ("on-demand by referencing them with `#steering-file-name`"), `auto` ("included when your request matches the description", needs `name` + `description`). Best practices: "One domain per file", "Explain why decisions were made", "Maintain Regularly … treat changes like code changes." https://kiro.dev/docs/steering/ [verified]
- **Where they disagree / critique.** Böckeler (martinfowler.com, 2025-10-15) separates *spec-first*, *spec-anchored* ("The spec is kept even after the task is complete") and *spec-as-source* ("the human never touches the code"). Criticisms: spec-kit "created a LOT of markdown files for me to review … I'd rather review code than all these markdown files"; one fixed workflow for every size ("neither of them is suitable for the majority of real life coding problems"; a small bug became four user stories, "using a sledgehammer to crack a nut"); false control: "the agent ultimately not follow all the instructions." She calls general context files (Kiro steering, spec-kit constitution) a **memory bank**, distinct from per-feature specs. https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html [verified]
- **Doctrina.** `docs/features/<name>.md` is already spec-first (write, execute, delete; lessons to DECISIONS). The gap is the *method* layer: neither tool documents "how to run a research fan-out", but Kiro's inclusion modes are the clearest prior art for *when* a method doc loads (always / by file path / by description / manual). Böckeler's warning maps directly: a single heavy template for every task would cost Pedro review time and usage; methods need size tiers (a lean path, as spec-kit's own guides offer [snippet: https://codemyspec.com/blog/github-spec-kit-guide]).

### 2.3 Plan, progress and handoff files
- **Community patterns, no standard.** Handoff skills converge on one file with Goal / Current Progress / What Worked / What Didn't Work, read at session start and updated at end; another variant prioritizes "Decisions Made" with reasoning. Matt Pocock's `/handoff` argues a file is only worth it when work moves to a new harness, directory, colleague or forked side task; otherwise `/compact` suffices; pass the path, not pasted text. Some setups generate the mechanical part with a PreCompact hook. https://aihero.dev/skills-handoff, https://skills.sh/jwa91/agentskills/session-handoff, https://tessl.io/registry/skills/github/ykdojo/claude-code-tips/handoff [snippet, all]
- **Doctrina.** The repo already does this ad hoc (the "Progress block" in this very brief; `tradition universe handoff` commit 7ead3ca). The "What didn't work" section is the raw material a retro needs; today it is deleted with the feature doc.

## 3. Classic engineering and organizational practices

### 3.1 Architecture Decision Records (Nygard, 2011)
- **Prescribes.** Problem: without rationale, newcomers either blindly accept or blindly reverse — "It's better to avoid either blind acceptance or blind reversal." Sections Title / Context / Decision / Status / Consequences; "If a decision is reversed, we will keep the old one around, but mark it as superseded"; "numbered sequentially and monotonically. Numbers will not be reused"; "one or two pages long"; stored in the repo. https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions [verified]
- **Doctrina.** `DECISIONS.md` is already an ADR log (date, what, why, discarded, "Replaced by"). Process changes ("from now on, research runs use pilot-then-fan-out") are decisions too and belong there with their why; the *method text itself* is not an ADR — it is the current state that ADRs justify. Keep that split: DECISIONS = why the method changed; playbook = the method as it is now.

### 3.2 Blameless postmortems (Google SRE book + workbook)
- **Prescribes.** Blameless: "focuses on identifying the contributing causes of the incident without indicting any individual or team." Triggers fixed in advance: "It is important to define postmortem criteria before an incident occurs." "An unreviewed postmortem might as well never have existed." Sharing: "Postmortem of the month", reading clubs, "Wheel of Misfortune." Without "some formalized process of learning from these incidents in place, they may recur ad infinitum." https://sre.google/sre-book/postmortem-culture/ [verified]
- **Action items (workbook).** "To our users, a postmortem without subsequent action is indistinguishable from no postmortem" (Treynor Sloss); items need an owner ("Actions items without clear owners are less likely to be resolved"), a priority, tracking as bugs, "a verifiable end state"; "trying to change human behavior is less reliable than changing automated systems and processes"; "Reward action item closeout"; "Templates make it easier to write complete postmortems." https://sre.google/workbook/postmortem-culture/ [verified]
- Practitioner reinforcement: undecided items drift unless explicitly closed or consciously dropped with a reason. https://incident.io/blog/why-post-mortem-action-items-die [snippet]
- **Doctrina.** Maps well: (a) define *in advance* which runs get a retro (e.g. any run with ≥3 subagents, any run that hit the usage cap, any run whose output Pedro rejected); (b) every retro ends in action items with a verifiable end state ("playbook X step 3 now says Y"), not prose lessons; (c) the SRE point that changing systems beats changing behavior is the argument for encoding lessons into a skill/hook/template rather than a "lessons learned" note; (d) "unreviewed = never existed" → Pedro or the next session must read/approve the retro's proposed changes, otherwise they rot.

### 3.3 After Action Review (US Army)
- **Prescribes.** Developed by the U.S. Army; "begins with a clear comparison of intended versus actual results achieved"; "Assigning blame or issuing reprimands is antithetical to the purpose of an AAR." https://en.wikipedia.org/wiki/After-action_review [verified, secondary; cites Morrison & Meliza 1999, DTIC ADA368651, which returned 403]. The four questions (What was supposed to happen? What actually happened? Why the difference? What to sustain/improve?) and "run it immediately after" appear across secondary guides [snippet: https://blog.itcilo.org/the-compass/methodologies/after-action-review/, https://asana.com/resources/after-action-review-template.md]; the canonical manual is TC 25-20, *A Leader's Guide to After-Action Reviews* (1993) [memory; official PDF not reached].
- **Difference from a postmortem.** AARs run after *every* exercise, success or not, and are short; postmortems run on failures past a threshold [memory, consistent with sources above].
- **Doctrina.** The AAR is the right shape for a run retro: 4 questions, 5 minutes, done by the coordinating session right after the run while the transcript is in context, with numbers (planned vs actual agents, % usage, rework passes, items Pedro rejected). Its "intended vs actual" first question only works if the plan was written *before* the run — so the pre-run plan and the retro are one artifact.

### 3.4 Runbooks / playbooks
- **Evidence.** Google SRE: "thinking through and recording the best practices ahead of time in a 'playbook' produces roughly a 3x improvement in MTTR as compared to the strategy of 'winging it'"; "no playbook … is a substitute for smart engineers able to think on the fly" but steps "are valuable when responding to a high-stakes or time-sensitive page." https://sre.google/sre-book/introduction/ [verified]
- **Doctrina.** The 3x figure is Google-internal and about incident response [verified as Google's claim, not independently replicated]. The analogue holds for repeated run types (source research, verification pass, consistency pass, design proposal): the expensive part today is re-deriving the plan. Caveat from the same text: playbooks guide judgment, they don't replace it — keep them at "right altitude" (§1.1) and Anthropic's "degrees of freedom" (low freedom only for fragile steps such as citation verification).

### 3.5 Checklists (Gawande / WHO)
- **Evidence.** WHO 19-item Surgical Safety Checklist, 8 hospitals, 7,688 patients: major complications "from 11 percent in the baseline period to 7 percent"; inpatient deaths "from 1.5 percent to 0.8 percent." https://news.harvard.edu/gazette/story/2009/01/surgical-safety-checklist-drops-deaths-and-complications-by-more-than-one-third/ [verified] (Haynes et al., NEJM 2009 [memory for citation details]).
- **Design rules (Boorman via Gawande).** Defined pause point; DO-CONFIRM (work from memory, then verify) vs READ-DO (step by step); short (5–9 items, "killer items" only). [snippet: https://www.shortform.com/blog/types-of-checklists/, https://janmeppe.substack.com/p/how-to-make-a-good-checklist]
- **Doctrina.** Anthropic's skill guidance converges on the same device ("a checklist that Claude can copy into its response and check off," §1.3). For agents, DO-CONFIRM fits end-of-run gates (did every claim get a tag? did the Progress block get updated? did the retro get written?); READ-DO fits fragile procedures. Keep each checklist to killer items — long checklists are the agent equivalent of an over-specified CLAUDE.md.

### 3.6 Docs-as-code and single source of truth
- **Prescribes.** Docs "with the same tools as code": issue trackers, version control, plain-text markup, code reviews, automated tests; "You can block merging of new features if they don't include documentation." https://www.writethedocs.org/guide/docs-as-code/ [verified]
- Rot mechanism: every merged change makes docs slightly less accurate and the fix is never prioritised; agents treat stale docs as ground truth and "ship the mistake." [snippet: https://fabric.so/blog/outdated-docs-are-worse-than-no-docs, https://prefactor.tech/blog/the-death-of-documentation — vendor blogs, opinion]
- **Doctrina.** Already practised (AGENTS.md "Hygiene": each fact in one file, fix contradictions on the spot, overwrite Current state). The new risk is *duplication between layers*: the same lesson in MEMORY.md, a playbook, a skill and DECISIONS. Needs one owner per fact type (method → playbook/skill; why it changed → DECISIONS; per-user preference → MEMORY).

## 4. Failure modes and loop-closing mechanisms

### 4.1 Failure modes
| Failure | Evidence | Relevance to Doctrina |
|---|---|---|
| **Context bloat from always-loaded instructions** | Context files raise cost >20% without improving success; agents obey them even when irrelevant (arXiv 2602.11988) [verified]. "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" (code.claude.com best-practices) [verified]. Chroma, 18 LLMs: "model performance varies significantly as input length changes, even on simple tasks"; "Even a single distractor reduces performance" https://www.trychroma.com/research/context-rot [verified] | Every always-loaded process line is paid by every subagent of every run, on a 5-hour cap. Process docs must not go in AGENTS.md beyond a one-line pointer. |
| **Playbooks/skills nobody reads** | NASA's lessons-learned system: lessons "not routinely identified, collected, or shared"; barriers "lack of time … and a perception of intolerance for mistakes" (GAO-02-195, https://www.gao.gov/products/gao-02-195) [verified]; 2012 NASA IG: managers "rarely consult or contribute" [snippet: https://www.nextgov.com/people/2012/03/nasa-knowledge-management-database-used-rarely/205923/]. Claude Code skill auto-activation: one community eval (Sonnet 4.5, 22 prompts × 2 runs) got 50–55% with no hook, 50–59% with a "simple instruction" hook, 100% with a forced-evaluation UserPromptSubmit hook https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals [verified; single author, small n, older model]. Anthropic itself warns "If Claude never accesses a bundled file, it might be unnecessary" [verified, §1.3] | A playbook that relies on the agent *remembering* to open it will be skipped roughly half the time if this holds. Loading must be explicit (`/name`, a coordinator brief that names the file, a `skills:` preload, or a hook), not hoped-for. |
| **Agents ignore the spec anyway** | Böckeler: "the agent ultimately not follow all the instructions" [verified, §2.2]; Anthropic harness post: agents "declare the job done" too early [verified, §1.7] | A playbook needs a verifiable gate at the end (DO-CONFIRM checklist, Stop hook, reviewer subagent), not just steps. |
| **Doc rot / contradictions** | Memory docs: contradicting instructions → "Claude may pick one arbitrarily"; `/doctor prompt-audit` finds "references to files or commands that don't exist" [verified, §1.2]. Kiro: "Maintain Regularly" [verified]. Rot as process failure [snippet, §3.6] | Playbooks reference file paths, agent names, models and quotas that change (e.g. the usage plan in MEMORY.md is dated). Needs dated "last validated" + audit at retro time. |
| **Retros whose lessons never change behavior** | "a postmortem without subsequent action is indistinguishable from no postmortem"; unowned items "less likely to be resolved"; "trying to change human behavior is less reliable than changing automated systems" (SRE workbook) [verified]. "An unreviewed postmortem might as well never have existed" (SRE book) [verified] | A "lessons" section in a feature doc that gets deleted, or a line in MEMORY.md, is the behavioral fix. The systemic fix is an edit to the playbook/skill/hook in the same retro, approved by Pedro. |
| **Process overhead exceeds value** | Böckeler: one heavyweight workflow for all sizes, "sledgehammer to crack a nut"; "I'd rather review code than all these markdown files" [verified]. Anthropic: plan mode "adds overhead … If you could describe the diff in one sentence, skip the plan" [verified] | Pedro's review time is the scarcest input. Plan + retro must scale with run size; tiny tasks get none. |
| **Over-reacting to reviewers** | "A reviewer prompted to find gaps will usually report some, even when the work is sound … Chasing every finding leads to over-engineering" [verified, §1.6] | Retro lessons should come from observed cost/error, not from a critic asked to find problems. |

### 4.2 Mechanisms that close the loop
1. **Explicit promotion ladder with triggers (Anthropic).** "Claude gets a convention or command wrong twice → Add it to CLAUDE.md"; "paste the same playbook … for the third time → Capture it as a skill"; "want something to happen every time without asking → Write a hook"; "A repeated mistake or a recurring review comment is a CLAUDE.md edit, not a one-off correction in chat." https://code.claude.com/docs/en/features-overview [verified]. Doctrina's AGENTS.md already has the first rung ("When the agent repeats a mistake … promote the correction to a rule").

## 5. Implications for Doctrina

### 5.1 What the sources agree on (constraints any design should meet)
1. **Method text must not be always-loaded.** Keep AGENTS.md to a one-line pointer; load the method only for its task type (ETH study, Anthropic CLAUDE.md guidance, Chroma) [§1.2, §4.1].
2. **Loading must be explicit, not remembered.** Auto-discovery of skills/docs is unreliable (~50% in one small eval); use `/name`, a coordinator brief that names the file, `skills:` preload, or a hook [§4.1].
3. **Plan before, retro after, as one artifact.** AAR's first question ("what was supposed to happen") needs a written plan; Anthropic's multi-agent and harness posts persist the plan/progress to files [§3.3, §1.7].
4. **Retros end in edits to the system, approved and owned**, not in prose lessons (SRE workbook, Anthropic promotion triggers) [§3.2, §4.2].
5. **Scale process to run size** (Böckeler, plan-mode overhead): a lean path for small tasks, full plan + retro only above predefined triggers [§2.2, §1.6].
6. **One owner per fact type**: method = playbook/skill; why it changed = DECISIONS.md; per-user preferences = auto memory [§3.1, §3.6].
7. **Measure.** Each retro records planned vs actual (agents, models, % of 5-hour session used, rework passes, items Pedro rejected) so the next run of that type has a baseline [§1.7, §4.2].

Doctrina-specific facts that shape the options: process lessons already live in Pedro's auto memory (`MEMORY.md`: model economy, usage guard, "lessons on agents"), which **subagents never load** [verified, §1.4] and which is per-user, not in git; `docs/features/<name>.md` is deleted at the end, so lessons die with it; several sessions run in parallel on one repo, so shared method files need a single writer (AGENTS.md already says one coordinator owns shared files); Pedro approves in Spanish, so retro proposals to him must be short and in Spanish while files stay in English.

### 5.2 Candidate shapes (not ranked)

**A. `docs/playbooks/` read on demand (docs-only).**
- Files: `docs/playbooks/<task-type>.md` (e.g. `research-fanout`, `verification-pass`, `consistency-pass`, `design-proposal`), each: when to use, effort table (agents/models/tool calls by size), delegation brief template, gates checklist (DO-CONFIRM), known failures, "last validated" date. Per-run plan + AAR in a run file (either inside `docs/features/<name>.md` with a mandatory "Retro" section, or a persistent `docs/runs/` log). AGENTS.md gets one row in the docs table: "Before any multi-agent run: read `docs/playbooks/<type>.md`".
- For: matches the existing doc system and hygiene rules; tool-agnostic (AGENTS.md standard); readable by Pedro; zero context cost until read; easy to review in git.
- Against: depends on the agent remembering to read it (the weakest link per §4.1); subagents only get it if the coordinator pastes or names it; no enforcement that the retro happens; risk of becoming GAO's "lessons system nobody consults."

**B. Project skills + custom agents (Claude Code-native).**
- Files: `.claude/skills/<run-type>/SKILL.md` (short workflow + checklist) with reference files one level deep and templates; `disable-model-invocation: true` so Pedro/coordinator triggers with `/research-run` etc. (no description cost, no misfires); `.claude/agents/<role>.md` (e.g. source-verifier) with `skills:` preload, `model:` set per the economy rule, and `memory: project` for role-specific lessons in `.claude/agent-memory/<role>/`; a `/retro` skill that writes the AAR and proposes diffs.
- For: native progressive disclosure; explicit trigger via slash command; preload solves subagent inheritance; per-role curated memory with enforced size cap; skill bodies survive compaction (first 5k tokens).
- Against: Claude Code-specific (other tools reading AGENTS.md won't see it); knowledge splits across skills, agent memory and docs (single-source risk); a loaded skill body stays in context for the whole run; agent-memory files are curated by the agent itself, so quality depends on review; more config surface for a junior owner to understand.

**C. Hybrid: docs as source, thin skills as entry points, one or two hooks as gates.**
- Files: method text in `docs/playbooks/` (single source, as A). Thin skills `/plan-run <type>` (reads the playbook, fills a run-file template, asks Pedro to approve scope in Spanish) and `/retro` (AAR 4 questions + metrics + proposed playbook diff + DECISIONS entry). Custom agents preload only the brief template. Optional hooks: SubagentStart injects "your brief and playbook are at X"; Stop/SessionEnd warns (not blocks) if a run file has an empty Retro.
- For: closes the loop structurally (plan → run → retro → playbook edit) while keeping one source of truth; explicit triggers; hooks enforce what memory can't; still readable as plain docs.
- Against: most moving parts; hooks are scripts to maintain and a blocking Stop hook could loop and burn the 5-hour cap; the indirection (skill → doc) can drift if the skill starts carrying method text; needs a rule that only the coordinator edits playbooks.

### 5.3 Open questions for the proposal
- Which run types get a playbook first (only those already repeated ≥2–3 times, per Anthropic's "third time" trigger)?
- Retro trigger criteria (e.g. ≥3 subagents, hit usage cap, Pedro rejected output) and who approves the resulting edits.
- Where run plans/retros live long-term: deleted with the feature doc (lessons extracted) or kept as a dated log for metrics.
- What to migrate out of Pedro's `MEMORY.md` into versioned method files, and what stays personal.
- Whether a blocking hook is acceptable on a usage-capped account, or warnings only.
